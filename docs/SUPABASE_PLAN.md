# Shared access and Supabase persistence plan

Status: approved design; database migrations, the trusted Edge adapter, shared-password UI, and the Angular persistence adapter are implemented. Local PostgreSQL, Auth/HTTP, and mobile browser tests pass. See [shared mode setup](SHARED_MODE.md), [database setup](SUPABASE_SETUP.md), and [Edge scheduling](EDGE_SCHEDULING.md). Hosted provisioning/deployment remain future phases. No hosted project or credentials have been configured.

## Shared password experience

Use one manually provisioned Supabase Auth account and one group. Everyone sees a single password field. The frontend supplies the shared account's configured email identifier to `signInWithPassword`; people never need to enter an email, register, or manage a personal profile. Supabase verifies the password and issues a separate authenticated session to each browser. Allow simultaneous sessions; do not configure single-session enforcement.

The shared account is an application account with group access, not a PostgreSQL superuser and not a Supabase dashboard account. Padel players remain independent records: adding Christopher as a player does not create an authentication account. Everyone using the shared password has the same application permissions.

Provision the account through the owner-controlled dashboard/admin tooling; disable public signups and anonymous sign-in. Keep recovery under an owner-controlled email address. The app has sign-in and sign-out, with session restoration on reload, but no registration, invitation, account editor, or user-management screens. Keep the entered password only long enough to submit it; never log it or save it in application storage. The Auth SDK manages the browser's session tokens.

This uses Supabase's [email/password authentication](https://supabase.com/docs/guides/auth/passwords) behind a password-only interface. Concurrent browser sessions are supported by [Supabase's session model](https://supabase.com/docs/guides/auth/sessions).

Accepted limits: changes are attributable to the shared account, not a particular person. A password holder has account access, including the ability to call underlying Auth APIs to change credentials, even without an account-settings screen. Removing one person's access requires changing the shared credentials and dealing with existing sessions. Password changes/sign-out must not be assumed to invalidate every already-issued access token instantly; membership removal blocks subsequent database authorization checks, while token expiry/revocation governs other authenticated access. These are consequences of the requested shared account, not reasons to add personal logins.

The password gates application data. Static HTML, JavaScript, and the login page remain publicly downloadable; a browser route guard alone is not database authorization.

## Proposed schema

Use UUID primary keys, `timestamptz` timestamps generated by the database, explicit foreign keys, and indexes on group/session/membership lookups. The first release has one seeded group and one membership. Group scoping keeps the authorization boundary explicit without adding a multi-user product interface.

| Table | Main fields | Purpose and constraints |
| --- | --- | --- |
| `groups` | `id`, `name`, `created_at` | The private padel group. Provisioned administratively; no public group creation. |
| `memberships` | `group_id`, `user_id` referencing `auth.users`, `created_at` | Primary key `(group_id, user_id)`. Initially one row for the shared account. No roles hierarchy is needed. Browser users cannot grant themselves membership. |
| `players` | `id`, `group_id`, `name`, `created_at`, `archived_at` | Stable identities across sessions. Trimmed nonblank names; case-insensitive uniqueness for unarchived names within a group. Archive instead of deleting historical players. No authentication user association required. |
| `sessions` | `id`, `group_id`, `status`, `court_count`, `match_points`, `rules_version`, `scheduler_version`, `revision`, `created_at`, `ended_at` | Active/ended states; one court; initial rules version fixes the total at 16 points. Nonnegative revision increases on every scheduling-relevant mutation. No requested match count. Ended state requires `ended_at`; active state has none. |
| `session_players` | `group_id`, `session_id`, `player_id`, `display_name_snapshot`, `roster_order`, `is_active` | Unique player per session, unique roster order. Initially all five/six are active. Name snapshot preserves historical display while statistics use stable player IDs. Session creation rejects archived players. Departures never delete historical membership. |
| `matches` | `id`, `group_id`, `session_id`, `sequence`, `status`, `match_points`, `score_a`, `score_b`, `published_at`, `confirmed_at`, `cancelled_at`, `confirmed_by`, `scheduler_version` | Unique `(session_id, sequence)`, positive sequence. Status published/completed/cancelled. At most one published match per session, enforced by a partial unique index. Completed scores are integers between zero and the stored total and sum exactly to that total. Other statuses have null scores/confirmation fields. Cancelled matches preserve the unplayed announced assignment when ending a session. |
| `match_participants` | `group_id`, `session_id`, `match_id`, `player_id`, `slot` | One row for every active player at publication, including resters. Slots `a1`, `a2`, `b1`, `b2`, `rest1`, `rest2`. Unique `(match_id, player_id)` and `(match_id, slot)`. Exactly four playing slots plus one/two resters. Immutable assignment snapshot. |

Do not create cumulative totals columns: points, matches played, rest counts, partnership/opponent frequencies, and profile graphs derive from completed matches. Membership count is unrelated to roster size.

Use composite foreign keys to enforce scope, not just application validation:

- `players` and `sessions` expose unique `(group_id, id)` keys.
- `session_players` references both its session and player through `group_id`.
- `matches` references its session through `group_id`; its stored points total must equal the session's immutable total through a composite foreign key.
- `match_participants` references `(group_id, session_id, match_id)` and `(group_id, session_id, player_id)` so a foreign group's player or another session's player cannot be attached.

Row checks cannot count children. Deferred constraint triggers, evaluated on final transaction state, validate five/six active session players, exactly two players per team, all active players assigned exactly once when publishing, and consistency between session status and published matches. An active session must have exactly one published match at commit; an ended session must have none. Historical matches retain their publication roster after later roster changes. Validate active-roster equality only for a newly published assignment, rather than reinterpreting old matches against today's roster.

Ordinary APIs cannot edit published participants, change stored rules, rewrite completed results, or delete history. Defer roster-change and correction endpoints until their explicit workflows exist. Reserve `match_corrections` for that later migration: append old/new scores, timestamp, shared-account actor, and reason, without changing the already published next assignment. Initial database writes reject corrections.

## RLS and write permissions

Enable RLS on every exposed table. Access is denied unless explicitly granted. `anon` has no data access. Authentication alone does not imply group membership.

| Caller | Read | Write |
| --- | --- | --- |
| Unauthenticated | None | None |
| Authenticated, no membership | None | None |
| Shared account with membership | Rows belonging to its group | Approved operations only, through controlled functions |
| Owner provisioning tools | Administrative bootstrap | Create shared account, group, membership; handle recovery |

For group-scoped SELECT policies, use `private.is_group_member(group_id)`, checking the current `auth.uid()` against `memberships`. Make this small helper `SECURITY DEFINER`, stable, with an empty fixed `search_path`, fully qualified references, and no dynamic SQL. The owner reads memberships without recursively invoking their RLS policy. Keep it in a non-exposed schema; grant only the schema usage/function execution needed for policy evaluation. Membership SELECT exposes only the caller's own membership; it does not call a policy that recursively reads itself.

Grant authenticated SELECT on the group-scoped tables, but revoke direct INSERT/UPDATE/DELETE. There are no permissive client write policies. Controlled player creation/rename/archive and session creation/end functions check membership themselves and perform validated writes. Do not permit browser changes to `groups` or `memberships`. Avoid a generic arbitrary-table write endpoint.

Privileged function execution can bypass RLS, so every such function must explicitly authorize its caller and validate derived group ownership. Derive the group from the locked session or stored player, rather than trusting a request's `group_id`. Revoke default function EXECUTE from PUBLIC and anon; grant only specific operations to authenticated. The score-commit function below is an exception with EXECUTE granted only to `service_role`, since the trusted Edge Function supplies its already verified caller identity. Do not grant authenticated callers its execution or allow them to supply a trusted actor ID.

This follows Supabase's [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) and [function privilege/search-path guidance](https://supabase.com/docs/guides/database/functions). If aggregate views are introduced, use invoker security so they obey underlying RLS; initially use the existing pure statistics functions over authorized records.

## Atomic score confirmation and next-match publication

Keep the existing TypeScript scheduler as the single scheduling implementation. A small Supabase Edge Function imports the pure domain module and invokes a transactional PostgreSQL RPC. This is a serverless adapter, without a separately hosted API server or a second scheduler port in SQL. Its purpose is to prevent a modified browser from supplying arbitrary next assignments while retaining the tested scheduler.

Browser request: `{ sessionId, matchId, scoreA, scoreB, requestId }`. The browser creates a UUID request ID once per confirmation and preserves it for retries. It never supplies the next teams, trusted user identity, authoritative version, or confirmation timestamp.

1. The Edge Function verifies the caller's access token with Supabase Auth and uses that identity, never a request-body user ID. It reads a consistent session snapshot through an invoker RPC under the user's token, so membership/RLS apply. Return roster, ordered completed history, current match, frozen rules/scheduler versions, and revision in one database statement/snapshot.
2. Validate scores and the expected published match. Simulate confirming that result in memory and call the existing scheduler to obtain the next assignment. Invalid input produces no writes. A retry for an already completed match still proceeds to the database's idempotency handling.
3. Using a server-only privileged client, invoke `commit_match_result` with verified user ID, request ID, scores, expected session revision, match ID, and the computed candidate. The RPC locks the session using `SELECT ... FOR UPDATE`. All session-changing RPCs lock this same row first, in the same order.
4. Under the lock, verify the actor is still a member of the session's group. Check prior request/result records before rejecting a stale revision. A replay must work even when later matches have already completed or the session has ended.
5. For a new completion, require an active session, matching revision, the same currently published match, compatible frozen rules/scheduler versions, valid integer scores, and a candidate containing exactly the active five/six players in legal slots. The trusted Edge Function computed scheduling priority; SQL enforces structural integrity and freshness.
6. Complete the old match; insert exactly one next match and all participant/rest snapshots; increase the session revision; insert the idempotency receipt. A next-match insert failure rolls back the entire completion. No HTTP calls occur while the database lock is held.
7. Commit and return the receipt containing completed match ID, original next match ID, stored scores, and revision. The UI refetches the authoritative current session separately, since the original next match might have completed by the time a late retry arrives.

The implementation normalizes receipts into two tables: `operation_receipts` stores group/request ID, operation kind, canonical payload (including scores), stable response (including committed revision), actor, and timestamp; `match_confirmations` links the completed match to its original receipt and next match. This also makes create/end requests idempotent and binds alternate request IDs for the same completed result. Unique `(group_id, request_id)` and unique completed `match_id` provide request-level and match-level idempotency. Both tables have group-member SELECT RLS and no direct client writes. Keep receipts as long as their match history.

- Same request ID and same match/scores: return the stored receipt.
- Same request ID with a different match or payload: reject as a conflict.
- Different request IDs confirming the same match with identical scores: return the original receipt; do not create another match.
- Same match with different scores: reject; corrections require their separate future endpoint.
- Simultaneous submissions: the session lock serializes them. The second transaction sees the first receipt/completion and applies the rules above.
- Revision changed before commit: no writes; the Edge Function reloads and recomputes, with bounded retries. A completed match or ended session returns its defined replay/conflict outcome instead of retrying indefinitely.
- End-session racing with confirmation: both lock the session. End-first rejects a new completion; confirm-first commits the result/next match, then end cancels that unplayed next match. No completed result disappears.

Use the same trusted scheduling adapter and revision-checked transaction pattern to create a session and its first match atomically. Make create/end requests idempotent too. Every mutation to session status, roster, results, or published assignments increments the revision. Creation does not publish an empty active session between requests. IDs/timestamps are generated by trusted code/database; gaps in sequence after explicit cancellation remain auditable.

The concurrency foundation is [PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html). A single [database function](https://supabase.com/docs/guides/database/functions) handles the write transaction; separate browser/Edge API calls would not be one transaction. Edge authentication must follow [Supabase's server-side caller verification guidance](https://supabase.com/docs/guides/functions/auth).

| 2 | `supabase/migrations/20261017000200_group_access.sql` | Enable RLS, private membership helper, SELECT policies, explicit table/function grants and revocations. Apply before exposing/seeding hosted data. |
| 3 | `supabase/migrations/20261017000300_session_operations.sql` | Confirmation receipts, locked/idempotent create/confirm/end RPCs, controlled player writes, immutable-history guards. Complete initial schema constraints and RPCs together before permitting app writes. |

The scheduling Edge Function, shared-password UI, and Supabase persistence adapter are implemented, with the pure domain unchanged. Database TypeScript types are generated from the local schema. `supabase/package.json` pins CLI/database/Edge/browser test tooling, and the frontend uses Supabase SDK 2.118.0 for Auth and authorized API access.

Provision the production shared Auth user outside migrations, then insert the group/membership through owner tooling. Do not create Auth users by hand-editing `auth.users`, seed production passwords, or commit a credential-bearing bootstrap script. Test fixtures use isolated local accounts only.

Do not automatically upload browser-local data or merge players by name. Default hosted mode starts empty while retaining existing browser data. An explicit, separately reviewed import can preserve valid UUID identities and history later. Hosted mode must never silently fall back to unshared local writes on a network error. Initially no offline score confirmation; failed submissions retain their request ID and offer retry.

## Security and verification before rollout

Frontend configuration contains only the Supabase project URL, publishable key, and shared account email identifier. The email is an identifier, not a secret. The entered password is submitted over HTTPS to Auth. Never embed a password/hash, secret key, service-role key, or database connection string in frontend files or frontend build-time environment variables. Values compiled into Angular are public even when sourced from environment variables.

The privileged credential is used only in Supabase's server-side Edge environment to invoke tightly scoped commit operations. It bypasses RLS, which is why explicit authorization in those operations is mandatory. Prefer the current publishable/secret key model when configuring supported tooling; never expose either a secret key or legacy service-role key. See [Supabase API key guidance](https://supabase.com/docs/guides/getting-started/api-keys).

Use Supabase Auth rate limits, HTTPS, generic failed-login feedback, and escaped Angular name rendering. Do not log passwords or bearer tokens. CORS permits the deployment/dev origins but is not authentication. Clear loaded group state on sign-out. Keep project/dashboard administration credentials private to the owner. Enable backups appropriate to retaining the group's history.

Implementation acceptance tests:

- Anonymous callers and authenticated nonmembers cannot read or mutate any table, including receipt/participant tables or through privileged RPCs. Test a second group to catch scope leaks even though the initial app has one group.
- A member cannot insert membership, directly edit results/participants, spoof another group/session/player, or execute the service-only commit RPC.
- Database rejects fractions, negatives, invalid totals, duplicate players/slots, missing team members/resters, extra active matches, and ended sessions with a published match. Accept 8–8 and 16–0.
- Concurrent same-score confirmations, different-score conflicts, reused request IDs, response-loss retries, stale revisions, failed next-match insertion, and end/confirm races produce the specified outcomes. Use independent database connections for real concurrency tests.
- One successful confirmation creates one completion and one next match. Repeated requests never advance another match. Failed transactions create neither. Ending preserves completed history and cancels the unplayed assignment.
- Compare server adapter assignments with existing scheduler fixtures for both roster sizes; rerun audit regressions. Verify rule totals agree between database, domain, and displayed UI.
- Verify sign-in from two browsers concurrently, password-only UI, session restoration, sign-out, error/loading states, and no browser-bundled privileged credentials.
- Run database/RLS tests, Edge integration tests, frontend lint/tests/build, and a local migration reset before applying migrations to an empty hosted project.
